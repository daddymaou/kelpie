title: The virtue of a small sync protocol
description: Keep storage, transport, and application policy as separate seams.

A sync library becomes easier to reason about when it makes fewer decisions on your behalf. Storage owns durable local state. Transport owns moving operations. The application owns identity, authorization, and domain meaning. The protocol is the contract between them — and the smaller that contract, the more durable it is across versions, runtimes, and time.

Kelpie's protocol is one versioned schema with three messages: a mutation, a push response, and a pull response. Everything else is composition.

## What the protocol must say

A mutation is a typed record with enough context to be interpreted anywhere:

```ts
{
  id: '01H8Z...',
  table: 'notes',
  rowId: 'n_01H8Z',
  op: 'insert' | 'update' | 'delete',
  fields: { body: '...' },
  hlc: 'eJz...',
  schemaVersion: 1,
  deviceId: 'device-A'
}
```

Each field is load-bearing. The `id` is unique and generated by the client, which is what makes pushing idempotent: the server can accept the same id twice and apply it once. The `hlc` is the hybrid logical clock stamp that orders concurrent mutations without wall-clock trust. The `schemaVersion` lets the server refuse traffic that predates a breaking change.

The push response is nearly as small: an `accepted` list of ids, a `rejected` list with reasons, and a cursor marking the server's new position. The pull response is a page of mutations, the next cursor, and a `hasMore` flag.

## What the protocol must not say

Tempting additions run straight into the seams the protocol is supposed to protect:

- **Credentials.** The protocol carries mutations, not identity. Authentication and authorization live in the transport and the server, so they can be reloaded, rotated, and replaced without versioning the data format.
- **Merging rules.** Conflict resolution is an application decision. A protocol that encodes a merge policy forces every client to agree on it forever.
- **Retry policy.** Backoff is a property of the client and the network in front of it, not a thing the wire format should dictate.
- **Envelope ceremony.** No acknowledgements, heartbeats, or handshakes that do not move mutations. Every one of them is something to maintain, test, and get wrong.

You can see the whole contract in the [protocol reference](/docs/library/configuration). At a glance it is a few hundred lines of Zod schema. That is a feature: the protocol is small enough to read end to end during a review.

## Additions cost a version

Once a server and a client ship, every change to the protocol must be negotiated. New optional fields are cheap. Renaming an existing one is a migration. Changing the meaning of a cursor is a coordination event.

The small-protocol discipline is a hedge against this: structure the protocol so that the parts most likely to change — auth, resolver, limits, retry — are layered *outside* the wire format instead of baked in. Then the protocol only changes when the data model actually changes, which is rare and deserves a version.

## Failures should stay visible

An adapter contract should preserve real errors, not turn them into an empty success. A blocked write is work that needs a decision; hiding it only makes the eventual recovery harder. The protocol's `rejected` list does not explain away a failure — it names each rejected mutation and the error code and message behind it. The client surfaces those as distinct states, and the queue shows them as such.

That is why the [adapter guide](/docs/library/adapters) emphasizes seam boundaries, and why the [offline queue](/docs/library/offline-queue) treats "rejected" differently from "pending". A small protocol keeps each of those meanings small, too.

## Small is not minimal

Small does not mean anemic. It means each moving part earns its place, is versioned when it changes, and does not secretly smuggle the application's policy into the plumbing. A protocol you can hold in your head is a protocol you can deprecate, migrate, and trust.
